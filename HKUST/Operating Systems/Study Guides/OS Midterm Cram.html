The OS decides who runs when (scheduling), keeps programs out of each other's memory (protection), hides the hardware behind simple calls (abstraction), and does it efficiently and fairly (resource allocation). An interrupt is hardware tapping the kernel on the shoulder. A trap is the program itself causing the switch.

BSay it like this

🗣️ Operating system

An OS is a resource allocator: it manages all resources and decides between conflicting requests for efficient and fair use. It is also a control program: it controls the execution of programs to prevent errors and improper use of the computer. The kernel is the one program running at all times.

🗣️ Interrupt, trap, system call

An interrupt is an external, asynchronous hardware event (timer, I/O completion) that transfers control to the kernel through the interrupt vector. A trap or exception is an internal, synchronous software event (division by zero, protection violation, or a system call request). Interrupts have priorities and are not all serviced the same way.

🗣️ DMA

With direct memory access, the device controller transfers blocks of data between its buffer and main memory without CPU intervention, raising one interrupt per block instead of one per byte. It reduces CPU involvement; it does not remove interrupts.

🗣️ Caching

Caching temporarily copies a subset of data from a slower, larger storage to a faster, smaller one. Average access time $= h \cdot t_{hit} + (1-h) \cdot t_{miss}$, so a high hit ratio alone does not guarantee good performance: hit time and miss penalty matter too. It works because of temporal locality (recently used data is used again) and spatial locality (neighbouring data is used soon).

🗣️ Dual mode

A mode bit distinguishes kernel mode (0) from user mode (1). Privileged instructions (I/O, timer, interrupt control) execute only in kernel mode. A timer interrupt guarantees the OS regains control of the CPU from a user program.

🗣️ Multiprocessors

Speedup with $N$ processors is less than $N$ because of contention on the shared bus and memory and coordination overhead. Asymmetric: a master processor schedules and does I/O. SMP: every processor performs all tasks, each with its own registers and cache, sharing memory. NUMA: each CPU has fast local memory and slower access to remote memory in one shared address space. Multicore: several cores on one chip, private L1, shared L2.

🗣️ System call and API

A system call is the programming interface to the services provided by the OS. Programmers use an API through a run-time library (libc) instead of raw system calls for convenience, portability and hiding implementation details. An API is not faster and cannot bypass protection. printf() is a library function that invokes the write() system call.

🗣️ Implementation

Each system call has a number; the system-call interface keeps a table indexed by that number, traps into the kernel, runs the handler and returns the status. Parameters pass in registers (limited count), in a block or table in memory whose address is in a register, or pushed on the stack. Block and stack place no limit on the number or length of parameters.

🗣️ Policy and mechanism

Policy is what will be done; mechanism is how it is done. The timer is a mechanism; how long to set it is policy. Separating them gives flexibility when policies change.

BSay it like this

🗣️ Process and PCB

A process is an instance of an executing program, consisting of an address space and one or more threads of control. The process control block stores its state, program counter, CPU registers, scheduling information, memory-management information, accounting information and I/O status.

🗣️ Context switch

A context switch saves the state of the running process into its PCB and loads the saved state of the next process. It is pure overhead; its cost depends on hardware support such as multiple register sets. It is not the same as a user-to-kernel mode switch.

🗣️ fork, exec, wait

fork() creates a child that is a copy of the parent; it returns the child's pid to the parent, 0 to the child, and a negative value on failure. Both continue from the instruction after fork. exec() replaces the process image with a new program and does not return on success. wait() blocks the parent until a child terminates and returns that child's pid and status. Linux implements fork with copy-on-write pages, so the address space is shared until written.

🗣️ Zombie and orphan

A zombie is a process that has terminated but whose parent has not yet called wait(), so its PCB entry and exit status remain. An orphan is a process whose parent terminated first; init / systemd adopts it and reaps it.

🗣️ Ordinary pipe

An ordinary pipe is unidirectional, usable only between a parent and child (inherited across fork), accessed through file descriptors fd[0] (read end) and fd[1] (write end), and ceases to exist when the processes finish. A named pipe (FIFO) needs no parent-child relation and persists after use.

🗣️ Three types of mode transfer

System call: a user process requests a service, like a function call outside the process. Interrupt: an external asynchronous event, independent of the process. Trap or exception: an internal synchronous event in the process (segmentation fault, divide by zero).

🗣️ Thread

A thread is the basic unit of CPU utilisation: a thread ID, a program counter, a register set and a stack. Threads of the same process share the code section, data section, heap, open files and signals. Benefits: responsiveness, resource sharing, economy, scalability.

🗣️ Concurrency vs parallelism

Concurrency: more than one task makes progress, possible on a single core by interleaving. Parallelism: tasks execute simultaneously, which requires multiple cores. Data parallelism splits the data and applies the same operation; task parallelism runs different operations.

🗣️ Amdahl's law

With serial fraction $S$ and $N$ cores, $\text{speedup} \le \dfrac{1}{S + \frac{1-S}{N}}$, which tends to $1/S$ as $N \to \infty$. The serial portion caps the speedup.

🗣️ Thread models

Many-to-one: many user threads on one kernel thread; one blocking call blocks all, no parallelism on multicore. One-to-one (Linux, Windows): more concurrency, but each user thread costs a kernel thread. Many-to-many and two-level: multiplex with optional binding.

🗣️ Signals and cancellation

A synchronous signal (illegal memory access, divide by zero) is delivered to the thread that caused it; an asynchronous signal (Ctrl-C, timer) goes to every thread or to a designated thread. Not every signal goes to every thread. Asynchronous cancellation terminates the target at once; deferred cancellation (default) lets the target check at cancellation points.

BSay it like this

🗣️ Metrics

CPU utilisation: fraction of time the CPU is busy. Throughput: processes completed per unit time. Turnaround: completion time minus arrival time. Waiting: time in the ready queue, which equals turnaround minus total CPU burst. Response: time from arrival to the first run.

🗣️ Exponential averaging

Predict the next burst as $\tau_{n+1} = \alpha\, t_n + (1-\alpha)\,\tau_n$. With $\alpha = 0$ recent history is ignored; with $\alpha = 1$ only the last actual burst counts; usually $\alpha = 1/2$.

🗣️ MLFQ

A multilevel feedback queue lets processes move between queues. A new process enters the top queue with a short quantum; a process that uses its whole quantum is demoted, so CPU-bound jobs sink and short interactive jobs stay on top. It approximates SRTF without knowing burst lengths, and aging (periodically moving jobs up) prevents starvation.

🗣️ Multiprocessor

Processor affinity: keep a thread on the same processor so its cache stays warm; soft affinity attempts it, hard affinity guarantees it. Load balancing: push migration (a periodic task moves work off busy CPUs) and pull migration (an idle CPU pulls work). Balancing conflicts with affinity. A memory stall is time spent waiting for memory; hardware threads per core (chip multithreading) let the core switch to another thread meanwhile.

🗣️ Real time

A periodic task has processing time $t$, deadline $d$ and period $p$ with $0 \le t \le d \le p$, rate $1/p$. Rate-monotonic: static priority, shorter period = higher priority; optimal among static-priority schemes. Earliest-deadline-first: dynamic priority, earliest deadline runs; does not require periodic tasks and can in theory reach 100% utilisation. Utilisation $= \sum t_i / p_i$. Hard real time: a missed deadline is a failure; soft: only a preference.

🗣️ Evaluation

Deterministic modelling: a fixed workload, exact numbers, valid only for that workload. Queueing models: Little's formula $n = \lambda W$. Simulation with trace tapes. Implementation: most accurate, most expensive.

📝 Q4.3 dynamic priority, S2026 
priority = initial + α·(time waited) + β·(time run); larger wins; tie → larger id; "checks every 3 units".
(a) α=0, β=3: the running process keeps gaining, never preempted. Waiting ones tie at 0 → larger id.
    0 P1 7 P3 13 P4 17 P2 22
(b) α=1, β=0, P1 and P2, checks every 3: waiting raises priority, running does not → they alternate.
    0 P1 3 P2 6 P1 9 P2 11 P1 12
(c) α=1, β=−2, start 30, checks every 3: runner loses 2 per unit, waiters gain 1 → rotate every check.
    0 P1 3 P2 6 P3 9 P4 12 P1 15 P2 17 P3 20 P4 21 P1 22
Method: a table of priorities, recompute at every check, pick the max with the stated tiebreak.
📝 Short question: "A new policy gives priority f_i = 1 / (CPU burst). I/O-bound favoured? Starvation?" 
Yes. I/O-bound processes have short CPU bursts, so their f_i is large and they are picked first.
Yes. A CPU-bound process with a long burst has a small f_i; if short jobs keep arriving it never runs (starvation).

BSay it like this

🗣️ Race condition (a short question last time)

A race condition occurs when several processes access and manipulate shared data concurrently and the outcome depends on the particular order in which the accesses take place. Example: two threads execute counter++ on counter = 5; each is load, add, store; both load 5 and both store 6, so one increment is lost.

🗣️ Critical-section problem

A solution must satisfy mutual exclusion (only one process in its critical section at a time), progress (if no process is inside and some want in, the selection cannot be postponed indefinitely), and bounded waiting (a bound on how many times others may enter before a waiting process gets its turn).

🗣️ Kernels and interrupts

A preemptive kernel allows a process to be preempted while in kernel mode, so kernel data can race, especially on SMP. A non-preemptive kernel runs until it exits kernel mode, blocks or yields, so it is essentially free of kernel race conditions on a single processor. Disabling interrupts protects a critical section on a uniprocessor but is inefficient on multiprocessors.

🗣️ Atomic instructions

test_and_set(&target) returns the old value and sets target to true, atomically. Lock: while (test_and_set(&lock)); /* CS */ lock = false;. compare_and_swap(&v, expected, new) sets v = new only if v == expected and always returns the old value. Lock: while (compare_and_swap(&lock, 0, 1) != 0);.

🗣️ Mutex lock and spinlock

A mutex lock has atomic acquire() and release(). A mutex whose acquire busy-waits is a spinlock: it wastes CPU cycles while spinning, but needs no context switch, so it is good when the lock is held briefly and on multiprocessors, where the holder runs on another core. With swap: while (swap(locked, 1) == 1);, release with locked = 0;.

🗣️ Semaphore

A semaphore is an integer accessed only through two atomic operations: wait(S) (while S ≤ 0 wait; then S--) and signal(S) (S++). A counting semaphore is initialised to the number of resource instances; a binary semaphore behaves like a mutex. In the blocking implementation, wait decrements and blocks if the value is negative, signal increments and wakes one if the value is still ≤ 0; a negative value's magnitude is the number of waiting processes.

🗣️ Deadlock and starvation

Deadlock: two or more processes wait indefinitely for an event that only one of the waiting processes can cause (P0: wait(S), wait(Q); P1: wait(Q), wait(S)). Starvation: indefinite blocking, for example a process never removed from a LIFO semaphore queue.

CSemaphore stepper: force the order C, B, A

S2026 Q5: A needs B and C done; B needs C done. Semaphores s0 = s1 = s2 = 0. Click a thread to run its next line; a blocked line will not advance. Try every interleaving: the output is always C, B, A.

🛠️ Semaphore ordering recipe (Q5 and MC23)
  1. Write the required order as arrows: "C before B", "B before A".
  2. One semaphore per arrow, all initialised to 0.
  3. The earlier thread does signal(sem) after its work. The later thread does wait(sem) before its work.
  4. Fill every blank; write /* Nothing */ where nothing is needed. Then trace one bad interleaving and confirm it blocks.

📝 Bounded-waiting mutual exclusion with test_and_set (the MC favourite) 
entry:  waiting[i] = true; key = true;
        while (waiting[i] && key) key = test_and_set(&lock);
        waiting[i] = false;
exit:   j = (i + 1) % n; while (j != i && !waiting[j]) j = (j + 1) % n;
        if (j == i) lock = false; else waiting[j] = false;   // hand the lock straight to j
Mutual exclusion: only the first test_and_set sees false. Progress: exit frees the lock or a waiter.
Bounded waiting: the cyclic scan gives everyone a turn within n − 1 entries.

DTry it

Three threads must print 1, 2, 3 in order. Semaphores and placement?
s12 = 0, s23 = 0. T1: print 1; signal(s12). T2: wait(s12); print 2; signal(s23). T3: wait(s23); print 3.
A blocking semaphore has value −3. Meaning? What happens on signal?
Three processes are blocked on it. signal makes it −2, still ≤ 0, so one blocked process is woken.
Why is while (test_and_set(&lock)); alone not bounded waiting?
A fast process can leave and re-acquire before a spinning process gets its test_and_set in, any number of times. The waiting[] version hands the lock to the next waiter in cyclic order.

ERecall

Outcome depends on access order: race condition. The three requirements: mutual exclusion, progress, bounded waiting. test_and_set returns the old value. Busy-waiting mutex: spinlock. Spinlock plus: no context switch; minus: wastes CPU cycles. Semaphore at −2 means two waiting. To force A before B: A does signal after, B does wait before.

Why it mattersRace conditions are the most expensive bug class in concurrent systems, from bank transfers to multiplayer games. Mutexes and semaphores are the tools in every language.
