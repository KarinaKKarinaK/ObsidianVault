Start from zero: the whole midterm in plain words

What an OS is. Your laptop has one CPU (or a few), some memory, a disk, a keyboard. Dozens of programs want to use them at once. The operating system is the referee and the butler: it decides who gets the CPU and when (scheduling), gives each program its own memory and keeps them from trampling each other (protection), hides messy hardware behind simple calls like "read this file" (abstraction), and does it all efficiently and fairly (resource allocation). The part of the OS that is always running is the kernel.
User mode and kernel mode. Ordinary programs run in user mode, a restricted mode where dangerous instructions (talk to the disk directly, change the timer) are forbidden. When a program needs something dangerous, it asks the kernel through a system call: the CPU flips to kernel mode, the kernel does the work, flips back. printf is a library function that eventually makes the write system call. An interrupt is the hardware tapping the kernel on the shoulder ("disk finished"). A trap is the program itself causing the switch (divide by zero, or a system call).
Process. A program sitting on disk is a file. A program running is a process: the code plus its memory (globals, heap, stack) plus where it is right now (program counter, registers). The kernel keeps a record card for every process, the PCB. A process is in one of five states: new, ready (wants the CPU), running (has it), waiting (blocked on I/O), terminated. Switching the CPU from one process to another means saving one record card and loading another: a context switch, pure overhead.
fork, exec, wait. On Unix you make a new process by cloning yourself: fork() makes an identical copy. Both copies continue from the same line. The only difference is the return value: the parent gets the child's pid, the child gets 0. To run a different program, the child calls exec(), which throws away its own code and loads the new program (so lines after exec never run unless exec failed). The parent calls wait() to pause until the child finishes. A child that finished but whose parent has not called wait yet is a zombie. Exam questions count how many processes a loop of forks creates: each fork doubles the number of processes that reach it.
Pipes. A pipe is a one-way tube between two related processes. pipe(fd) gives two file descriptors: fd[0] to read, fd[1] to write. After fork both processes have both ends, so each closes the end it does not use. close(0); dup(fin); makes a file become standard input so that scanf reads from the file.
Threads. A thread is a worker inside a process. All threads of a process share the code, globals, heap, and open files, but each has its own stack, program counter, and registers. Creating or switching threads is cheap because the memory map does not change. Concurrency means making progress on several tasks by taking turns on one core. Parallelism means several cores really working at the same instant. Amdahl's law says the part of a program that cannot be parallelised caps your speedup: if 25% is serial you never beat $4\times$ no matter how many cores.
Scheduling. When several processes are ready, which one gets the CPU? FCFS: first come first served, simple but a long job makes everyone wait (convoy). SJF: shortest job first, optimal for average waiting time but you cannot know the future. SRTF: SJF with preemption. RR: everyone gets a time slice $q$ in turn, good response time. Priority: highest priority first, risk of starvation, fixed by aging. MLFQ: several queues; new jobs start in the top queue with a short slice, a job that uses its whole slice is demoted. Short interactive jobs stay on top, CPU hogs sink. Real-time: RM gives fixed priority to the task with the shortest period; EDF always runs the task whose deadline is soonest and misses fewer deadlines.
Three numbers you always compute. Turnaround = finish time minus arrival time. Waiting = turnaround minus CPU burst (time spent in the ready queue). Response = time of first run minus arrival. Average them over all processes.
Synchronization. Two threads doing counter++ at the same time can lose an update because counter++ is really three instructions (load, add, store) and they can interleave. That is a race condition. The fix is to make the dangerous part a critical section that only one thread enters at a time. Tools: hardware atomic instructions (test_and_set, compare_and_swap), a mutex lock built on them (a spinlock busy-waits, no context switch, wastes CPU), and semaphores, an integer with wait (decrement, block if it would go negative) and signal (increment, wake one). A semaphore initialised to 0 is a "you may go" ticket: thread B does wait(s) before its work, thread A does signal(s) after its work, so A's work always happens before B's.
Why this is easy. The MC questions are slide facts, and the exam is open book. The long questions are four mechanical procedures: count forks, draw a Gantt chart under stated rules, fill a C skeleton with pipe/dup/read/write, and place wait/signal to enforce an order. Each has a template below and a simulator to check yourself.

Chapter 1. Introduction

Must-know facts (MC come straight from these)
  • OS = resource allocator (efficient and fair use of CPU, memory, I/O) and control program (prevents errors and improper use). Kernel = the one program running at all times. System programs ship with the OS but are not the kernel. Middleware = frameworks like databases.
  • Von Neumann: instructions and data in the same memory, accessed by address. CPU has control unit (IR, PC), ALU, registers. Cycle: fetch, decode, fetch operands, execute, write back.
  • Devices and CPU share a common bus to memory. Device controllers have local buffers and signal completion with an interrupt. Interrupts have priorities; they are not all serviced the same way. The kernel handles them.
  • Interrupt (hardware, asynchronous) vs trap / exception (software: error or system call, synchronous). Interrupt-driven I/O: the CPU checks for interrupts between instructions, saves state, runs the handler, restores.
  • DMA: for fast devices. The controller moves blocks between device and memory directly, one interrupt per block, less CPU involvement. It does not remove interrupts; CPU and DMA run concurrently.
  • Storage hierarchy: registers, cache, main memory (volatile, DRAM, byte addressable, the only big store the CPU accesses directly), SSD/NVM, HDD, tape. Faster means smaller and more expensive. Bootstrap program lives in EEPROM/firmware.
  • Caching: copy a hot subset from a slower bigger store to a faster smaller one. Average access time $= h \cdot t_{hit} + (1-h) \cdot t_{miss}$. A high hit ratio alone does not guarantee performance: hit time and miss penalty matter too. Works because of temporal and spatial locality.
  • Dual mode: mode bit, kernel 0, user 1. Privileged instructions (I/O, timer, interrupt control) only in kernel mode. A timer interrupt guarantees the OS regains control. Intel has rings 0 to 3.
  • Multiprocessors: speedup with $N$ processors is less than $N$ (bus and memory contention). Benefits: throughput, economy of scale, reliability. Asymmetric (master/slave) vs SMP (each processor does everything). Multicore = several cores on one chip with private L1 and shared L2. NUMA = each CPU has fast local memory and slower remote memory.
  • Multiprogramming: keep the CPU busy by holding several jobs in memory. Timesharing: switch so often that users can interact. Needs process management, CPU scheduling, swapping, virtual memory.
  • Virtualization: a VMM/hypervisor runs guest OSes on one host. Cloud: virtualization delivered over the network, pay per use; SaaS, PaaS, IaaS.
  • Units: KB, MB, GB are powers of 1024 for memory; networking speeds are in bits per second.
Try it: a cache has hit time 1 ns, miss penalty 100 ns, hit ratio 0.95. Average access time? Would a 0.99 hit ratio with a 400 ns miss penalty be better?
$0.95 \cdot 1 + 0.05 \cdot 100 = 5.95$ ns. Second: $0.99 \cdot 1 + 0.01 \cdot 400 = 4.99$ ns, better. But with a 1000 ns miss penalty it would be $10.99$ ns, worse despite the higher hit ratio. That is the point of the short question.
Why it mattersAn OS is the referee for every program you will ever ship. Interrupts, DMA, and caching explain why your code is fast on one machine and slow on another, and why a database engineer cares about memory hierarchy.

Chapter 2. OS structures

Must-know facts
  • Services for the user: user interface (CLI, GUI, touch), program execution, I/O operations, file-system manipulation, communication (shared memory or message passing), error detection (errors can occur in CPU, memory, I/O devices, and user programs, not only memory and I/O). Services for the system: resource allocation, logging/accounting, protection and security.
  • System call = the programming interface to OS services. Programmers use an API (POSIX, Win32, Java) through a library like libc. Why API instead of raw syscalls: convenience, portability, hides implementation details. APIs are not faster and cannot bypass protection.
  • Implementation: each syscall has a number; the kernel keeps a table indexed by number; the library stub traps into the kernel, which runs the handler and returns status. printf() (library) calls write() (system call). Entering printf does not immediately enter kernel mode.
  • Parameter passing: in registers (limited), in a memory block whose address is in a register, or on the stack. Block and stack have no limit on count or length.
  • Six syscall categories: process control, file management, device management, information maintenance, communications, protection. read(fd, buf, count) returns bytes read, 0 at end of file, -1 on error.
  • Linker combines object files and libraries into an executable; loader puts it in memory and does relocation. DLLs are loaded once and shared.
  • Policy vs mechanism: policy = what will be done, mechanism = how. The timer is a mechanism; how long to set it is policy. Separating them gives flexibility.
  • MS-DOS: single task, no process created when running a program, no dual mode. FreeBSD: multitasking, the shell forks then execs.

Why it mattersSystem calls are the only door between your program and the hardware. Knowing the monolithic versus microkernel trade-off is the same reasoning you use when choosing a monolith versus microservices at work.

Chapter 3. Processes

Must-know facts
  • Process = program in execution: text (code), data (globals), heap (grows up, malloc), stack (grows down: parameters, return addresses, locals), PC and registers. Program = passive file; process = active.
  • States: new, ready, running, waiting, terminated. Transitions: admitted (new to ready), scheduler dispatch (ready to running), interrupt or time slice over (running to ready), I/O or event wait (running to waiting), I/O or event completion (waiting to ready), exit (running to terminated). A process leaves running when it issues an I/O request, is preempted, or exits. Calling a function or reading cache does not.
  • PCB holds: state, PC, registers, scheduling info (priority, queue pointers), memory-management info, accounting, I/O status (open files). Linux: task_struct.
  • Context switch: save the state of the running process into its PCB, load the next one. Pure overhead, depends on hardware (register sets). Not the same as user-to-kernel mode switch.
  • Queues: ready queue and device wait queues. Long-term scheduler controls the degree of multiprogramming (I/O-bound vs CPU-bound mix). Short-term (CPU) scheduler runs every few milliseconds. Medium-term: swapping.
  • Creation: parent creates children, forming a tree. Child may share all, some, or none of the parent's resources. fork() returns child pid to parent, 0 to child, negative on failure. Copy-on-write: pages are shared until written. exec() replaces the image and does not return on success. wait() returns the pid of a terminated child and its status. exit() ends the process.
  • Zombie: terminated, but the parent has not called wait, so its PCB entry (with exit status) remains. It still has a pid. Orphan: parent exited first; init/systemd adopts it. Cascading termination: some systems kill all children when the parent dies.
  • IPC: shared memory (fast, kernel only at setup, producer-consumer with a bounded buffer; buffer of size $N$ holds $N-1$ items, empty when in == out, full when (in+1) % N == out) vs message passing (send/receive through the kernel; direct vs indirect via mailboxes; blocking vs non-blocking; rendezvous when both block; zero, bounded, unbounded buffering).
  • Ordinary pipes: unidirectional, parent-child only (inherited through fork), accessed like file descriptors, disappear when the processes end, not accessible by arbitrary processes. fd[0] read end, fd[1] write end. Named pipes (FIFO): no parent-child relation needed, persist after use, bidirectional on Windows. Sockets: IP plus port; ports below 1024 are well known.
Fork counting recipe (Q3.1 and an MC every year)
  1. Walk the code line by line. At each fork(), every process that reaches it becomes two: parent (return value pid, nonzero) and child (return value 0).
  2. Track who continues the loop and who leaves (break, return, exit, or an exec that succeeds).
  3. If each iteration turns one active process into $k$ active ones, after $n$ iterations there are $k^n$ active. Count stopped processes separately and add.
  4. Count outputs per process: each process prints whatever it reaches.

fork / exec failure cases (Q3.2) Always list three scenarios: (1) fork and exec succeed: child prints up to exec only, parent prints after wait. (2) fork succeeds, exec fails: child also prints the lines after exec. (3) fork fails: only the else branch runs. If there is no wait, say the parent and child output can interleave in any order.

Try it: how many processes does this create? for (i=0;i<3;i++) { if (fork()==0) continue; else break; }
Iteration 0: P0 forks C1; C1 continues, P0 breaks. Iteration 1: C1 forks C2; C1 breaks, C2 continues. Iteration 2: C2 forks C3; C2 breaks, C3 continues and the loop ends. Total 4 processes, a chain (each child of the previous), not a tree with fan-out.
Try it: process A forks B, B terminates immediately, A runs for an hour without wait. What is B? What if A also exits?
B is a zombie for the hour: terminated, pid and PCB kept for the exit status. When A exits without waiting, init adopts B and reaps it. If instead B were still running when A exited, B would be an orphan adopted by init.
Why it mattersfork, exec, wait, and pipes are the primitives behind shells, CI runners, and process supervisors. Zombies and orphans are real bugs in production services that spawn workers.

Chapter 4. Threads and concurrency

Must-know facts
  • Thread = basic unit of CPU utilization: thread id, program counter, register set, stack. Threads of one process share code, data, heap, open files, signals. They do not each have their own address space or file descriptors.
  • Benefits: responsiveness, resource sharing, economy (creating and switching threads is cheaper than processes), scalability (use multiple cores). Threads of the same process can run on different cores at the same time.
  • Concurrency: more than one task makes progress, possible on a single core by time multiplexing. Parallelism: tasks run at exactly the same time, needs multiple cores. Debugging multicore programs is harder, not easier.
  • Multicore programming challenges: identifying tasks, balance, data splitting, data dependency, testing and debugging. Data parallelism (same operation, data split) vs task parallelism (different operations).
  • Amdahl's law: $speedup \le \dfrac{1}{S + \frac{1-S}{N}}$ with $S$ the serial fraction and $N$ cores. Limit as $N \to \infty$ is $1/S$. Example: $S=0.25$, $N=2$: $1/(0.25+0.375)=1.6$. S2026 MC17: 61% parallel ($S=0.39$) on 3 cores: $1/(0.39+0.61/3)=1.69$.
  • User threads (library: Pthreads, Windows, Java) vs kernel threads (scheduled by the OS). Models: many-to-one (one block blocks all, no parallelism), one-to-one (Linux, Windows; more concurrency, kernel cost per thread), many-to-many, two-level.
  • Implicit threading: thread pools (bounded number of threads, reuse), fork-join, OpenMP, Grand Central Dispatch.
  • fork with threads: some systems have two versions, duplicate all threads or only the caller. exec replaces all threads.
  • Signals: synchronous (caused by the thread itself: illegal memory, divide by zero) go to the causing thread; asynchronous (Ctrl-C, timer) may go to all or to a chosen thread. Users can define handlers; different signals can have different handlers; not every signal goes to every thread. kill(pid, sig) vs pthread_kill(tid, sig).
  • Cancellation: asynchronous (immediate) vs deferred (default; target checks at cancellation points). pthread_create, pthread_join, pthread_cancel.
  • Linux: threads and processes are both tasks created with clone(); flags CLONE_VM, CLONE_FS, CLONE_FILES, CLONE_SIGHAND decide what is shared. Windows: one-to-one, ETHREAD, KTHREAD, TEB.
Try it: a program is 90% parallel. Speedup on 4 cores? On infinitely many?
$S=0.1$. $1/(0.1 + 0.9/4) = 1/0.325 = 3.08$. Infinite cores: $1/0.1 = 10$.
Try it: which of these is per thread, which per process: stack, heap, open files, program counter, global variables, signal handlers
Per thread: stack, program counter (and registers). Per process, shared by all threads: heap, open files, globals, signal handlers.
Why it mattersThreads and Amdahl's law decide whether buying a 64-core machine helps. Every performance review of a service starts with "what fraction is serial".

Chapter 5. CPU scheduling

Must-know facts
  • Execution alternates CPU bursts and I/O bursts. Many short bursts, few long ones. I/O-bound: many short CPU bursts. CPU-bound: few long ones.
  • Scheduling decisions happen when a process: (1) goes running to waiting, (2) terminates, (3) running to ready (interrupt), (4) waiting to ready or new arrival. 1 and 2: non-preemptive. 3 and 4: preemptive.
  • Dispatcher: context switch, switch to user mode, jump to the right place. Dispatch latency = time to stop one and start another.
  • Metrics: CPU utilization (fraction busy), throughput (processes per unit time), turnaround (completion minus arrival), waiting (time in ready queue = turnaround minus burst), response (first run minus arrival).
  • FCFS: non-preemptive, convoy effect (short jobs stuck behind a long one). Slide example bursts 24, 3, 3: average wait 17 in order P1 P2 P3, but 3 in order P2 P3 P1.
  • RR: quantum $q$, preempted job goes to the tail. No process waits more than $(n-1)q$. Large $q$ becomes FCFS; small $q$ needs $q \gg$ context switch time. Rule of thumb: 80% of bursts shorter than $q$. RR has better response, often worse turnaround than FCFS when jobs are equal length. Slide example $q=4$ on 24, 3, 3: wait 6, 4, 7, average 5.67; response 4, 7, 10.
  • SJF: pick the shortest next CPU burst. Optimal average waiting time. Problem: predicting the burst. Exponential averaging $\tau_{n+1} = \alpha t_n + (1-\alpha)\tau_n$, usually $\alpha = 1/2$; $\alpha=0$ ignores recent history, $\alpha=1$ uses only the last burst. Preemptive version = SRTF; slide example (0,8),(1,4),(2,9),(3,5): P1 P2 P4 P1 P3, average wait 6.5. Starvation of long jobs possible.
  • Priority: smallest number = highest priority in the textbook convention (the exam may say the opposite, read it). Preemptive or not. Equal priority: FCFS. Starvation, fixed by aging. SJF is priority scheduling with priority = predicted burst. Priority with RR: same priority share RR.
  • Multilevel queue: fixed queue per process type, each queue its own algorithm, fixed-priority preemptive scheduling between queues or time slicing (60/20/10/10).
  • MLFQ: processes move between queues. Parameters: number of queues, algorithm per queue, when to upgrade, when to demote, which queue a process enters. Textbook example: Q0 RR 8 ms, Q1 RR 16 ms, Q2 FCFS. New job enters Q0 and preempts Q1/Q2 jobs; using the whole quantum demotes; a preempted Q1/Q2 job rejoins the head of its queue with its remaining quantum. Approximates SRTF without knowing bursts, good response time, "fair" to CPU-bound jobs. Starvation handled by periodically moving everyone to the top queue. Slide example average wait 16.8.
  • Thread scheduling: PCS (process contention scope, library schedules user threads onto LWPs by programmer priority) vs SCS (system contention scope, kernel schedules kernel threads). One-to-one systems use only SCS.
  • Multiprocessor: asymmetric (one master does all scheduling and I/O, can bottleneck) vs SMP (each processor self-schedules from a common or private ready queue). Multicore puts several cores on one chip for speed and power, it complicates scheduling. Memory stall: waiting on memory; hardware threads per core (chip multithreading, hyperthreading) let the core switch to another thread. Two levels of scheduling: OS picks a software thread for a logical CPU, the core picks which hardware thread runs. Processor affinity: keep a thread on the same CPU for cache reasons; soft vs hard (sched_setaffinity). Load balancing: push migration (periodic task moves work off busy CPUs) and pull migration (idle CPU pulls); conflicts with affinity.
  • Real time: hard (deadline miss = failure) vs soft (just preference). Periodic task: processing time $t$, deadline $d$, period $p$, $0 \le t \le d \le p$, rate $1/p$. Admission control. RM: static priority, shorter period = higher priority; optimal among static-priority schemes; utilization $\sum t_i/p_i$. Slide example 25/50 + 35/80 = 94%, P2 misses its deadline at 80 (finishes at 85). EDF: dynamic priority, earliest deadline first; does not need periodic tasks; theoretically can reach 100% utilization; same example meets all deadlines.
  • Evaluation: deterministic modeling (exact numbers for a given workload), queueing models (Little's formula $n = \lambda W$: 7 arrivals per second and 14 in queue means 2 s wait), simulation (trace tapes), implementation.
Gantt chart procedure (write it down, follow it mechanically)
  1. Make a table: process, arrival, burst, remaining, queue (for MLFQ), remaining quantum.
  2. Keep a time cursor. At every event time (arrival, quantum expiry, completion) decide who runs next using the stated rule and tiebreak.
  3. For preemptive schemes, an arrival can interrupt the running process immediately. Note what happens to the preempted process (tail of queue in RR, head of queue in the exam MLFQ rules, keeps remaining quantum).
  4. Write the chart as "0 P1 4 P2 8 P3 12 ..." with boundary times.
  5. Waiting time per process = completion minus arrival minus burst. Response = first start minus arrival. Average over processes. Show the per-process numbers; they carry partial credit.
The exam's MLFQ rules (S2026 Q4.1), worked Q0 RR 4 ms, Q1 RR 8 ms, Q2 FCFS. New arrivals enter Q0 and preempt lower queues immediately. Full quantum used means demotion. Preemption alone does not demote. A preempted Q1/Q2 job goes to the head of its queue.
Processes (arrival, burst): P1 (0, 9), P2 (2, 25), P3 (6, 7), P4 (14, 18), P5 (45, 15), P6 (58, 6).

At 14, P4 arrives in Q0 and preempts P1, which goes to the head of Q1 with 3 left and quantum remaining. At 18, P4 drops to Q1 (behind P1, P2, P3? No: Q1 order is by when they joined: P1 at the head because it was preempted, then P2, P3; P4 joins the tail). At 45 P5 arrives and preempts P2 which is in Q2 by then. At 58 P6 preempts P5 (Q1). Waiting: P1 12, P2 44, P3 19, P4 45, P5 20, P6 0; average 23.33. Response: 4, 6, 6, 4, 4, 4; average 4.67.

RM: priority order by period, P1 > P2 > P3 > P4. Fill the chart task by task: place every P1 instance first at its release, then fit P2 around it, then P3, then P4. In the official answer P4 never gets the CPU in 0 to 16 and misses both deadlines; P3 misses both of its deadlines too. 4 missed deadlines. Chart from the official answer: 0 P1 1 P2 3 P3 4 P1 5 P2 7 P3 8 P1 9 P3 10 P2 12 P1 13 P3 14 P2 15 P1 16.
EDF: at every slot run the released task with the earliest absolute deadline. Official chart: 0 P1 1 P2 3 P4 4 P3 6 P1 7 P2 9 P1 10 P3 12 P4 13 P2 15 P1 16. P1 misses its 4th deadline (15, finishes 16) and P2 its 3rd (14, finishes 15). 2 missed deadlines. EDF misses fewer, which is the expected conclusion.
Method tip: write a column of absolute deadlines per task before drawing anything. For EDF, at each release re-sort by deadline.
Dynamic priority with $\alpha$ and $\beta$ (S2026 Q4.3) Priority = initial + $\alpha \times$ (time waited) + $\beta \times$ (time run). Larger value wins; tie goes to the larger id (as stated). "Checks every 3 units" means decisions only at multiples of 3.
(a) $\alpha=0$, $\beta=3$: a running process keeps gaining, so no preemption ever; among waiting processes all have priority 0, tie to larger id. Order: P1 (0 to 7), then P3 (id larger than P2, 7 to 13), P4 (13 to 17), P2 (17 to 22).
(b) $\alpha=1$, $\beta=0$, P1 and P2 only, checks every 3: waiting raises priority, running does not, so they alternate at checkpoints: 0 P1 3 P2 6 P1 9 P2 11 P1 12.
(c) $\alpha=1$, $\beta=-2$, start 30, checks every 3: running loses 2 per unit while waiters gain 1, so at each check the CPU rotates: 0 P1 3 P2 6 P3 9 P4 12 P1 15 P2 17 P3 20 P4 21 P1 22.
Procedure: keep a table of priorities, recompute at every check time, pick the max with the stated tiebreak, run until the next check or completion.
Try it: SRTF on P1 (0, 8), P2 (1, 4), P3 (2, 9), P4 (3, 5). Chart and average waiting time?
0 P1 1 P2 5 P4 10 P1 17 P3 26. Waiting: P1 $17-0-8=9$, P2 $5-1-4=0$, P3 $26-2-9=15$, P4 $10-3-5=2$. Average 6.5. Check it in the simulator.
Try it: exponential averaging with $\alpha = 0.5$, $\tau_0 = 10$, bursts 6, 4, 6, 4. Predictions?
$\tau_1 = 0.5\cdot6+0.5\cdot10 = 8$, $\tau_2 = 0.5\cdot4+0.5\cdot8 = 6$, $\tau_3 = 0.5\cdot6+0.5\cdot6=6$, $\tau_4 = 0.5\cdot4+0.5\cdot6 = 5$.
Try it: RM with P1 (20, period 50) and P2 (35, period 100). Utilization and schedulable?
$20/50 + 35/100 = 0.75$. P1 runs 0 to 20, P2 20 to 55 but P1 is released at 50 and preempts: P2 runs 20 to 50, P1 50 to 70, P2 70 to 75. All deadlines met.
Why it mattersScheduling is the heart of Kubernetes, of your laptop staying responsive while compiling, and of real-time control in cars and drones. MLFQ is what Windows and BSD actually run.

Chapter 6. Synchronization tools

Must-know facts
  • Race condition: several processes access and manipulate shared data concurrently and the outcome depends on the particular order of access. Example: counter++ and counter-- are each three machine instructions (load into register, add, store); interleaving with counter = 5 can leave 4 or 6 instead of 5. Kernel example: two forks racing on next_available_pid can hand out the same pid.
  • Critical section: code that touches shared data. Structure: entry section, critical section, exit section, remainder section. A solution must give: (1) mutual exclusion, (2) progress (if nobody is inside, the choice of who enters cannot be postponed forever), (3) bounded waiting (a limit on how many times others enter before a waiting process gets in).
  • Kernel: preemptive kernel allows preemption in kernel mode, so race conditions are possible and harder on SMP. Non-preemptive kernel runs until it exits kernel mode, blocks, or yields, so it is essentially race-free on a single processor.
  • Uniprocessor trick: disable interrupts. Inefficient on multiprocessors.
  • Atomic hardware instructions (non-interruptible):
    test_and_set(&target): returns the old value and sets target to TRUE. Lock: while (test_and_set(&lock)); /* CS */ lock = false;
    compare_and_swap(&value, expected, new): if value == expected set value = new; always returns the old value. Lock: while (compare_and_swap(&lock, 0, 1) != 0); /* CS */ lock = 0;
    Atomic variables: increment built on a compare_and_swap loop.
  • Bounded-waiting mutual exclusion with test_and_set: waiting[i] = true; key = true; while (waiting[i] && key) key = test_and_set(&lock); waiting[i] = false; critical section; then scan j = (i+1) % n cyclically for the first waiting[j]; if none, lock = false, else waiting[j] = false (hand the lock directly to j). Mutual exclusion: only the first test_and_set sees false. Progress: exit sets lock false or frees a waiter. Bounded waiting: at most $n-1$ turns. test_and_set does not release the lock.
  • Mutex lock: acquire() (busy wait while not available, then take) and release(), both atomic. A busy-waiting lock is a spinlock: wastes CPU cycles, but no context switch, so good when the lock is held briefly and on multiprocessors (spin on one core while the holder runs on another). With the atomic swap(x, v): while (swap(locked, 1) == 1);
  • Semaphore (Dijkstra, P and V): integer with atomic wait(S) (while S ≤ 0 busy wait; S--) and signal(S) (S++). Counting semaphore: initialised to the number of resource instances. Binary: 0 or 1, like a mutex. Ordering: semaphore synch = 0; P1 does S1 then signal(synch); P2 does wait(synch) then S2. Guarantees S1 before S2.
  • Semaphore without busy waiting: struct with value and a waiting list. wait: value--; if value < 0, add to list and block(). signal: value++; if value ≤ 0, remove one process and wakeup(P). A negative value's magnitude = number of waiting processes.
  • Deadlock: two processes each wait for a signal only the other can give (P0: wait(S), wait(Q); P1: wait(Q), wait(S)). Starvation: indefinite blocking, e.g. LIFO semaphore queue.
Semaphore ordering recipe (Q5, 8 points, and MC23)
  1. Write the required order as arrows: "C before B", "B before A", "C before A".
  2. One semaphore per arrow, all initialised to 0.
  3. The earlier thread does signal(sem) after its work. The later thread does wait(sem) before its work.
  4. If an arrow is implied by others (C before A follows from C before B before A) you can still use the given semaphore; the exam told you which semaphores exist. Fill every blank, writing /* Nothing */ where nothing is needed.
S2026 Q5: A depends on B and C, B depends on C. Given: A does wait(&s1), B ends with signal(&s2), C ends with signal(&s1). Blanks: A also wait(&s2) (B before A); B starts with wait(&s0) (C before B); C starts with nothing; C also does signal(&s0) after printing. Output always C, B, A.
MC23 pattern: sem = 0, worker2 waits on it first, worker1 posts after its update, so worker1 always goes first: "A 2; B 5;".
Reading a semaphore program for output Track the value. Initial 0 means the first wait blocks until a signal. Initial 1 means one thread passes, the rest queue. A mutex around the shared update does not decide the order, only prevents interleaving inside the update. The order comes from semaphores and from which thread can pass first.
Try it: three threads must print "1", "2", "3" in that order. They start in random order. Semaphores and placement?
s12 = 0, s23 = 0. T1: print 1; signal(s12). T2: wait(s12); print 2; signal(s23). T3: wait(s23); print 3.
Try it: a semaphore has value $-3$ in the blocking implementation. What does that mean? What happens on signal?
Three processes are blocked on it. signal makes the value $-2$, which is still $\le 0$, so one blocked process is woken and moved to the ready queue.
Try it: why is while (test_and_set(&lock)); alone not bounded waiting?
A fast process can leave the critical section and re-acquire the lock before a spinning process gets its test_and_set in, repeatedly. Nothing limits how many times that can happen. The waiting[] array version fixes it by handing the lock to the next waiter in cyclic order.
Why it mattersRace conditions are the most expensive bug class in concurrent systems, from bank transfers to multiplayer games. Mutexes and semaphores are the tools you will use in every language.

The lab's own "exam example": two pipes for two-way talk (Lab 4) 
char buffer[10] = {};  int p2c[2], c2p[2];
pipe(p2c);  pipe(c2p);                      // BLANK1, BLANK2
pid_t pid = fork();
if (pid == 0) {                             // child
    const char msg[] = "Child";
    close(c2p[0]);  write(c2p[1], msg, 6);  // BLANK3: send "Child" (6 bytes with the null; 5 accepted)
    close(p2c[1]);  read(p2c[0], buffer, 7); // BLANK4: receive "Parent" (7 bytes; 6 accepted)
    printf("Child received the message: %s\n", buffer);
} else {                                    // parent
    const char msg[] = "Parent";
    close(c2p[1]);  read(c2p[0], buffer, 6); // BLANK5
    close(p2c[0]);  write(p2c[1], msg, 7);   // BLANK6
    printf("Parent received the message: %s\n", buffer);
}
Pattern: name pipes by direction (p2c, c2p), each side closes the end it does not use, write the whole string including the terminating null, read the same count. A single pipe is one-way; a process that writes then reads the same pipe may read its own message.
Lab 4: named pipes, popen, pthreads
  • Named pipe (FIFO): mkfifo(name, 0777) creates it as a file; unrelated processes open it with open(name, O_WRONLY) or O_RDONLY, then read and write as usual; it persists until deleted. open blocks until both ends are open (use O_NONBLOCK to avoid). Data read is consumed, so no broadcasting; writes up to PIPE_BUF bytes are atomic. Check existence with access(name, F_OK).
  • popen / pclose: FILE *fp = popen("ls", "r") forks a child running the command and returns a stream connected to its stdout ("w" connects to its stdin); pclose(fp) waits for it and returns its status.
  • Pthreads: pthread_create(&tid, &attr, runner, arg), pthread_join(tid, NULL), pthread_exit(0), pthread_attr_init(&attr). Compile with -lpthread. Threads share globals (the lab's sum). Join ten threads with a for loop.
  • Thread-order trace questions: main creates T1 and T2 then joins both: outputs "main: begin", then A and B in either order (T2 can run before T1, or both before main reaches the joins), then "main: end". Without a join, main may finish first.
Lab 5: PA2 MLFQ rules (likely to be reused in a question) N-level feedback queue, N from 1 to 4, at most 10 processes, last queue is FCFS, input sorted by arrival, first arrival at 0, no equal arrival times, CPU never idle, at most 300 Gantt steps. Walkthrough: a new arrival goes to the end of Q0 and preempts a lower-queue process; a process that uses its full quantum moves to the end of the next queue; a finished process leaves. Run ./mlfq < input.txt > output.txt and compare with diff --side-by-side.
Why it matters These seven calls are how every shell, web server, and container runtime starts programs and wires their inputs and outputs together. Docker, systemd, and your terminal are fork, exec, pipe, and dup in a loop. Understanding them is the difference between using a computer and running one.
